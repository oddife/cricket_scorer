# Sync Identity Architecture Decision

**Status:** Locked for the next synchronization implementation phase.

The project will use separate identities for local storage, client-created records, server canonical records, and synchronization operations. This decision was made after clearing the test matches so the real tournament can start from a clean data state.

## Entity identity

Every entity created by any client (Web, Android, iPhone/iPad, Windows) receives a client-generated UUID called `app_id` immediately at creation time. This happens even when the client is offline.

The Supabase server generates a permanent `global_id` when the entity is first synchronized. `global_id` is the canonical cross-device identity and never changes.

The existing integer `local_id` remains the local Drift/SQLite database identity only. It must never be used as a cross-device identity.

`sync_id` is reserved for synchronization bookkeeping (a synchronization operation/version/event). It is **not** the identity of a Player, Team, Match, Innings, Ball, Tournament, or other domain entity.

## Required model

```text
local_id   -> local database identity only
app_id     -> permanent client-created UUID
            -> unique across Web/mobile/desktop clients
            -> never changes

global_id  -> permanent server-generated UUID
            -> canonical shared identity
            -> never changes

sync_id    -> synchronization operation/version identity
            -> not a domain entity identity
```

## Offline creation

An offline-created record may initially have:

```text
local_id  = 42
app_id    = <UUID generated by the client>
global_id = NULL
```

After first successful synchronization:

```text
local_id  = 42
app_id    = <same UUID>
global_id = <server-generated UUID>
```

Other devices may have different `local_id` values while retaining the same `app_id` and `global_id`.

## Collision handling

`app_id` must be generated as a UUID v4 (or another cryptographically random UUID implementation). Web and mobile can therefore create records concurrently without relying on sequential numeric IDs. A matching person/name is not considered an ID collision; automatic merging by name must not occur.

## Cross-entity references

Once a `global_id` exists, synchronized domain relationships and match/event references should use the canonical global identity rather than a bare local integer ID or `source_installation_id + local_id` pair.

During the offline period, local records may use their `app_id`/local database relationship as appropriate. Synchronization resolves the record to `global_id` without changing the original `app_id`.

## Source of truth

Drift/SQLite remains authoritative for offline scoring and persisted local match facts. Supabase is the shared synchronization/distribution layer. Synchronization must not be required for live scoring.

## Migration/testing rule

All existing test matches have been deleted. Do not create new tournament/test match data until the three-ID identity implementation is complete and verified.

The first verification should create a small test match and verify the same Team/Player identities across Web, Windows, and mobile, including a record created offline and synchronized later.

## Important invariant

**Never replace `app_id` with `global_id`, never replace `global_id`, and never use `local_id` as a cross-device identity.**
